# Migration review: launch-privacy-prep against production (2026-10-31)

Production runs commit **3ef4e97**, which is also the rollback target, with that commit's schema files applied. Everything below was proven on local Postgres 17 with Supabase's default grants simulated (every new table and function granted to anon and authenticated). Nothing was run against production.

Evidence:
- `test/migration-review.test.mjs` (3 tests)
- `test/conversion-then-cleanup.test.mjs` (2 tests)
- the 3ef4e97 server suite run against the new SQL
- the new server's route tests run against the old SQL

## The release as one script

`migrations/2026-10-31-release.sql` is generated by `scripts/build-release-sql.mjs`. It applies these files in this order inside ONE transaction:

1. `migrations/2026-10-31-device-attribution.sql`: two nullable columns and an index. It's a no-op on a fresh database, where schema-billing creates them.
2. `schema-billing.sql`: `agni_reserve` gains `p_device_subject default null`. The 22-argument version is dropped in the same file.
3. `schema-community.sql`, `schema-misses.sql`: comment changes only. Views are re-created with `create or replace`, and their options and grants are unchanged.
4. `schema-deletion.sql`: `agni_delete_device_data`, `agni_delete_subscription_history`, `agni__deletion_open`, `agni__deletion_alert`.
5. `schema-retention.sql`: `agni_retention_cleanup`, `agni_beta_signup_cleanup`.
6. `schema-contributor-migration.sql`: two backup or count tables, plus the `agni_contrib_*` functions.
7. `schema-dish-cleanup.sql`: one backup table, plus the `agni_dish_cleanup_*` functions.
8. `schema-lockdown.sql`: LAST. It revokes anon and authenticated from every `agni*` function and table, and enforces RLS and security_invoker.

**Why one transaction.** Applied file by file, the first apply leaves **18 functions callable by anon and authenticated, and 3 backup tables readable**, until lockdown runs. The functions include `agni_delete_device_data`, `agni_delete_subscription_history`, `agni_retention_cleanup`, `agni_contrib_apply`, `agni_contrib_rollback`, `agni_dish_cleanup_apply` and `agni_dish_cleanup_rollback` (measured). Postgres DDL is transactional, so inside one transaction no PostgREST request ever sees that state. A test injects a failure just before lockdown: the database is left exactly as it was.

| Question | Result | Evidence |

| Existing data changed by the apply | No. Every pre-existing table has an identical row fingerprint; new columns are NULL; new tables are empty | test 1 |
| Second apply (file by file, or the release script) | **0 changes**: function signatures and bodies, grants, RLS, view options, columns, constraints, data | tests 1 and 2 |
| Re-running `schema-billing.sql` alone, before lockdown | 0 functions become anon-callable. `create or replace` keeps grants, and the drops are no-ops the second time | test 1 |
| Overloads | Exactly one `agni_reserve` after the release | test 1 |
| Deployed server (3ef4e97) against the new SQL | 212 of 215 pass, the same as its own baseline (1 fatsecret import failure, 2 app-body skips). The new `p_device_subject` defaults to NULL, so the old named-argument call still resolves | 3ef4e97 suite with the new SQL |
| New server against the old SQL | Fails: every metered request returns 503, because the old `agni_reserve` has no `p_device_subject`. 45 of 69 route and deletion tests fail | branch suite with the 3ef4e97 SQL |
| Fresh-database order bug | Found and fixed: the device-attribution migration failed on an empty database (no billing tables yet). It is now guarded with `to_regclass` | 3ef4e97 suite run |

## Required order and why

1. **SQL before server.** The new server passes `p_device_subject`; the old SQL rejects it, and every AI request would fail. The old server works on the new SQL, so applying SQL first carries no downtime.
2. **Lockdown last, in the same transaction.** That closes the exposure window.
3. **Contributor conversion after the server deploy.** Before the deploy, the old server writes raw install IDs; afterwards it writes hashes. Converting after deploy leaves no raw rows behind. If it's done earlier, re-running apply is safe and catches any stragglers.
4. **Test-dish cleanup after conversion.** It still matches correctly either way: `conversion-then-cleanup` proves the raw pairs find all 33 rows in converted form, and that the reverse order ends with identical rows. Only the delete count differs, when a test install has a hashed twin (none exist in production today).

## Irreversible steps and realistic rollback

| Step | Undone by redeploying 3ef4e97? | Rollback mechanism | Limit |
|---|---|---|---|
| Release SQL (columns, functions, backup tables) | Not needed: 3ef4e97 runs on it unchanged | Leave it in place | **Never re-apply the 3ef4e97 SQL.** It recreates the 22-argument `agni_reserve` beside the new one, and every reservation fails "is not unique" (tested) |
| Server deploy | Yes | Vercel instant rollback or promote to the 3ef4e97 deployment | Rows written by the new server keep their `device_subject`; harmless to the old server |
| Contributor conversion | No | `contrib-migrate` rollback from `agni_dish_contrib_backup_20261031` | Only while the backup exists. A row the same phone re-wrote after conversion is replaced by its snapshot |
| Test-dish cleanup | No | `test-dish-cleanup` rollback from `agni_dish_cleanup_backup_20261031` | Only while the backup exists. Restores the converted form if run after conversion (tested) |
| Retention cleanup runs | No | None in-app | Permanent. Supabase keeps 7 daily physical backups (verified 2026-10-31); **PITR is OFF**, so recovery is a whole-database restore to a daily point, losing everything since |
| Beta-email cleanup | No | None | Same as retention |
| Dropping a backup table | No | None | Do not drop without Shine's approval; the runbook keeps them |
| Deletion requests from users | No | None, by design | Intended |
